## 1. 剧情模式进程

### 1.1 结构总览

共 **8 章**，章节即现实赛事名：CSP-J → CSP-S → NOIP → 省选 → NOI → CTT → CTS → IOI。
每章 3–5 关，**正赛恒为本章最后一关**；前面的关位依次为热身赛、模拟赛Ⅰ–Ⅲ：

| 章节 | 序号 | 关数 | 关位序列 | 首通钱基数 M | 正赛里程碑 U |
|---|---|---|---|---|---|
| CSP-J | 1 | 4 | 热身 / 模Ⅰ / 模Ⅱ / **正赛** | 500 | 改名卡×1 |
| CSP-S | 2 | 4 | 热身 / 模Ⅰ / 模Ⅱ / **正赛** | 1,200 | 洗练券×1 |
| NOIP | 3 | 5 | 热身 / 模Ⅰ / 模Ⅱ / 模Ⅲ / **正赛** | 3,000 | 定心丸×2 |
| 省选 | 4 | 5 | 热身 / 模Ⅰ / 模Ⅱ / 模Ⅲ / **正赛** | 8,000 | 进阶石×1 |
| NOI | 5 | 5 | 热身 / 模Ⅰ / 模Ⅱ / 模Ⅲ / **正赛** | 20,000 | 进阶石×2＋心流引擎×1 |
| CTT | 6 | 3 | 热身 / 模Ⅰ / **正赛** | 45,000 | 进阶石×3 |
| CTS | 7 | 3 | 热身 / 模Ⅰ / **正赛** | 90,000 | 紫级书自选券×1 |
| IOI | 8 | 4 | 热身 / 模Ⅰ / 模Ⅱ / **正赛** | 180,000 | 传说礼盒 |

- M、关位系数 S（1.0 / 1.3 / 1.6 / 2.2 / 2.8）、每关道具池与里程碑 U 的完整定义以 GAME-DESIGN §13.2 为准，本文不改写、不复制数值公式以外的部分。
- 每关是一场 §8.1 排名制模拟赛（3–4 题），具体题目参数、NPC 选手池规模与实力模板见 `docs/data/stages.yaml`。
- tag 获取卡为 **PVP 独占**，剧情模式任何环节均不发放。

### 1.2 章节解锁链 【定稿】

- **章间线性**：第 n 章的**正赛首通**后，第 n＋1 章整章解锁。游戏初始仅第 1 章（CSP-J）开放。
- **章内亦线性**：章内按关位顺序逐关解锁（前一关通关才解锁下一关）。理由：章内难度本身递增，线性解锁引导玩家按曲线培养，避免开局直撞正赛劝退。
- 已通关的关卡**永久可重复进入**（刷名次奖金，见 §1.9）；解锁状态永不回收。

### 1.3 参赛资格：单人出战 【定稿】

**每关由恰好 1 名学员出战**，从玩家全部在册学员中任选，无绑定、无状态门槛；开赛（模拟开始）后不可更换人选。

采用单人出战的理由：

1. §8.1 排名制模拟赛以**个人总分**对 NPC 池排位；多名学员同场会出现「自己和自己抢名次」，既稀释与 NPC 的竞争感，也会让名次奖金可被多人分摊套利。
2. 每道题锚定单一六维，「按本场题目主导维度派对应强项学员」因此成为每一关的核心阵容决策——这是单人制独有的策略深度。
3. 战报叙事聚焦一人，养成情感投射更强。
4. 体力核算与失败重试规则最简洁（见下）。

出战硬性要求仅一条：**出战学员当前体力 ≥ 本次出战消耗**（§1.4）。心态低、天赋差均可上场，风险自担（心态影响专注获取效率，可能拖累发挥）。

### 1.4 出战体力消耗 【定稿】

| 章节 | 每次出战扣减体力（出战学员） |
|---|---|
| CSP-J / CSP-S / NOIP / 省选（第 1–4 章） | **1 点** |
| NOI / CTT / CTS / IOI（第 5–8 章） | **2 点** |

- 高级别赛事更耗神，符合直觉，也让后期重试有真实的机会成本。
- 数值唯一定义处：`economy.yaml` → `story.stamina_cost`；服务端开赛接口校验，客户端仅展示。

### 1.5 失败与重试 【定稿】

- **完赛未达通关线**（名次低于 §1.6 通关线）或中途弃赛＝未通关：**无任何惩罚**——不扣钱、不扣声誉、不解锁任何负面状态。
- 可**立即重打**，次数不限；每次重打重新扣体力，并以新随机种子重掷本场 NPC 发挥（上一场的残局不作保留）。
- 体力上限 5（GAME-DESIGN §4）天然限制单学员单日的尝试次数，无需额外次数限制。
- 比赛内心态波动的**持久化规则归 `systems/contest.md`**；本文仅提出建议：模拟赛（非真实赛事）的心态净变动在结算落盘时**减半**，避免「重试惩罚化」与本节的无惩罚原则冲突。

### 1.6 通关判定与首通奖励发放流程 【定稿】

**通关线**：本场完赛且最终名次 ≤ **8**——固定前 8 名（集成终裁：与 NPC 选手池规模解耦，避免「前 50%」类公式随 stages 配置漂移；与前八名才有名次奖金的设定互相呼应。配置键：`stages.yaml → defaults.pass_rank_max`）。

**首通存储**：`user_stage_progress(user_id, stage_id, ng_layer)` 记录 `first_cleared_at`；**每个 NG+ 层独立记录**（§1.8）。该四元组加唯一约束。

**发放流程**（与结算同一数据库事务内完成）：

1. 判定本场是否为该 `(stage, layer)` 的首通（查询 `first_cleared_at` 是否为空）；
2. **是首通**：发放钱 `round(M[章节] × S[关位])`（NG+ 层再乘 `1 + 0.5k`，进阶石类里程碑不乘算，见 §1.8）→ 从该章道具池按关位权重抽取 n[章节] 件道具（NG+ 第 k≥2 层池稀有度上移一档、彩封顶）→ 若本场为**正赛**，追加发放里程碑 U[章节]（**仅 k=0 一周目发放**；NG+ 层不重复发 U，进阶石产出由每层全通固定 +5 承担——GAME-DESIGN §13.3）；
3. **非首通**：改为按 §1.9 结算名次奖金（同样要求进入前 8）；
4. 写入 `first_cleared_at` 并提交；战报页展示完整奖励摘要。

**幂等保障**：`first_cleared_at` 的唯一约束保证并发重放/接口重试不会双发奖励；礼盒类道具（如传说礼盒）入背包后需手动开启，开启所得在 `items.yaml` 中定义。

### 1.7 一周目全通判定与传奇教练勋章 【定稿】

- **判定**：一周目（layer 0）下 8 个章节正赛的 `first_cleared_at` **全部非空**，在最后一次通关结算的事务末尾触发一次性检测。
- **发放**：
  - 大额结算金 **500,000**（`economy.yaml → story.fullclear_bonus_gold`）；
  - **传奇教练勋章**（`badge-legend`）×1——账号永久被动：声誉获取 +10%（`items.yaml` 定义）；
  - 金牌陈列座（`trophy-gold`）×1，荣誉陈列品；
  - **解锁 NG+ 第 1 层**。
- 触发时**全服公告**（社区规模小，仪式感优先）。
- 勋章为账号级全局唯一（stack 1），注销/重开不转移。

### 1.8 NG+ 层级规则

层级 k ≥ 1，整数编号；规则框架出自 GAME-DESIGN §13.3，此处补充推进细则：

- **开启**：一周目全通（§1.7）解锁第 1 层。
- **逐层推进** 【定稿】：第 k 层内 8 章正赛**在该层的首通状态全部点亮**后，结算发放该层全通奖励——**进阶石 ×5（固定，不参与任何乘算）**＋专属徽章 `badge-ngplus-k`（运行时按层生成的陈列勋章，不在 `items.yaml` 枚举）——并解锁第 k＋1 层。层数无上限。
- **难度缩放**（引用 §13.3，实现读取 `economy.yaml → contest.ngplus_*`）：题目数值需求 ×`(1 + 0.15k)`；特性触发概率 ＋`10%·k`；特性等级池上移（彩封顶）。
- **奖励缩放**：首通钱部分 ×`(1 + 0.5k)`；道具池稀有度自 k≥2 起上移一档（彩封顶）；**进阶石里程碑一律不乘算**（稀缺性红线，GAME-DESIGN §7.3）。
- **首通状态独立存储** 【定稿】：`(user_id, stage_id, ng_layer)` 三元组各自独立记录首通。因此：同一关在 layer 0 与 layer 2 的首通互不相干；在高层通关不会回头「补写」低层状态；回低层/一周目重打只会得到名次奖金，不影响任何层的首通记录。章节选择页按层切换显示各自的进度与可重复通关标识。

### 1.9 重复通关名次奖金收益表 【定稿】

非首通的关卡，完赛且进入前 8 时发放**名次奖金**：

**公式**：`prize = round(M[章节] × 名次系数 × (1 + 0.5 × ng_layer))`

- 名次系数：冠军 0.3 / 亚军 0.2 / 第三至八名 0.1（GAME-DESIGN §13.3）。
- **不乘关位系数 S**（设计取舍）：若乘 S，高关位（×2.2/×2.8）会让「每章最后一关」成为唯一值得刷的点并放大后期通胀；统一按章基价让各关刷金效率一致，刷点选择回归「哪章性价比高」而非「哪一关贵」。
- **每日限额**：同一关卡每日最多 **3 次**名次奖金结算；超出次数仍可正常打，但不再发放奖金（防脚本化刷金，`economy.yaml → story.daily_rank_prize_cap_per_stage`）。
- NG+ 层按乘数放大，下表为一周目（layer 0）基数：

| 章节 | M | 冠军（30%） | 亚军（20%） | 3–8 名（10%） |
|---|---|---|---|---|
| CSP-J | 500 | 150 | 100 | 50 |
| CSP-S | 1,200 | 360 | 240 | 120 |
| NOIP | 3,000 | 900 | 600 | 300 |
| 省选 | 8,000 | 2,400 | 1,600 | 800 |
| NOI | 20,000 | 6,000 | 4,000 | 2,000 |
| CTT | 45,000 | 13,500 | 9,000 | 4,500 |
| CTS | 90,000 | 27,000 | 18,000 | 9,000 |
| IOI | 180,000 | 54,000 | 36,000 | 18,000 |

> NG+ 第 k 层＝表值 ×`(1 + 0.5k)`，例如 IOI 冠军在 NG+3 层为 54,000 × 2.5 ＝ 135,000。后期刷金收益显著抬升属预期设计（后期支出端同样膨胀），其总量由每日限额与体力竞争共同约束，最终以 M5 收支模拟验证。

## 2. PVP 赛制全流程

### 2.1 流程总览

```
管理员创建锦标赛 → 全服公告 → 玩家报名（门票＋锁定出战学员与携带预制题快照）
  → 报名截止：服务端生成对阵树并公示
  → 定时批量模拟（排队逐场结算，逐轮公示）
  → … → 决赛 → 冠亚军表演加场 → 结算发奖（公示领奖）
```

全程**异步定时驱动**，无实时对战；玩家不需要双方同时在线。

### 2.2 锦标赛创建（管理员）【定稿】

| 参数 | 说明 |
|---|---|
| `name` | 赛事名，1–32 字符 |
| `size` | 规模：**8 / 16 / 32** 人三档 |
| `registration_open_at / close_at` | 报名时间窗；建议窗口 ≥ 24h（服务端仅校验先后顺序） |
| `rewards` | 名次 → 奖励（item id ＋数量）映射；创建时校验 item id 存在于 `items.yaml`；默认模板见 §2.8 |
| `description` | 可选公告文案 |

流程：校验管理员角色 → 写入 `pvp_tournaments`（status: `announced`）→ **全服公告**（站内公告列表 ＋ 在线用户 toast）。
**奖励配置在创建时冻结**，开赛后（含报名期内？不——报名截止前允许修正，截止后冻结）不可变更；一切变更写审计日志（§2.9）。

### 2.3 报名与快照锁定 【定稿】

- **资格**：持有 `entry-ticket`（报名券）≥ 1、未报名本届、有在册学员。
- **消耗**：提交报名时扣除 **entry-ticket ×1**。设置门票的理由：给报名一个真实成本，抑制多开小号占坑与随手报名后弃赛；门票单价低且首轮获胜即返票（§2.8），长期参与者近似免票——成本精确落在低参与诚意的行为上。
- **锁定内容**：
  - **出战学员 1 名**（不设替补——出题对决是单学员行为，替补规则徒增复杂度）；
  - **携带预制题至多 2 道**：须为本账号学员出题库中质量评级达标的预制题（评级公式见 `systems/contest.md`），用途见 §2.6。
- **快照**：报名提交时即对出战学员属性/天赋与携带题数值做快照；**报名截止时刻**统一冻结全员快照（sha256 随对阵树公示）。截止前可随时撤销报名（**全额退票**）或修改学员/携带题；**截止后一切不可变更**，缺席无处罚概念（全自动赛程），仅当学员数据异常（如已被开除）时其场次判负。

### 2.4 对阵树生成 【定稿】

报名截止后服务端立即生成：

- 实际报名数 B ＜ 4 → 赛事取消，全员自动退票并公告。
- 否则取 bracket ＝ `2^ceil(log2(B))`（不超过声明的 size 上限时用声明值封顶）；B 非 2 的幂时，差额部分设**轮空位（bye）**，随机分配——轮空者首轮自动晋级。
- **种子位随机洗牌**（小社区无积分体系前的最公平解；未来可切换为历史战绩 seeding，接口预留 `seed_policy` 字段）。
- 对阵树持久化并**全服公示**；每场对决预分配 `match_slot`，作为模拟种子的推导成分（§2.5）。

### 2.5 定时批量自动模拟 【定稿】

- 服务端调度器（cron）**每轮一个固定时间点**执行（建议本地时间每晚 21:00，**轮间隔 ≥ 24h**，留出战报查阅期）；将当轮全部对决推入内部队列**排队逐场串行结算**，复用 §8.2 出题对决内核（平局 → PVP 分流：突然死亡加赛，细节见 `systems/contest.md`）。
- **为什么排队逐场结算而非实时**：双方无需同时在线；不存在网络抖动导致的公平性争议；结算全程服务端完成、可离线复核与重放审计。代价只是「没有直播感」，由逐轮公示＋战报分享弥补。
- **确定性**：每场 RNG 种子 ＝ `hash(tournament_id, round, match_slot, snapshot_hash)`，同输入重跑逐字节一致，争议可复核。
- 每场产出 `duel_record` ＋ 战报；轮次结束后公示晋级树更新与全部战报入口。
- 场外**不扣体力/精力**：自动离线赛制下体力模型不适用，报名门票即是参与成本；场内的精力表现由对决引擎按快照数据自行演算。

### 2.6 己方题库入赛与声誉收益 【定稿】

- 报名时可提交 **N = 2 道**自制预制题进入本届赛场题池（`economy.yaml → pvp.submitted_problems_max`）；须为本账号学员所出、质量评级达标（见 `systems/contest.md`）。
- **使用方式**：对决中某局轮到「作答 A 方出的题」时，**优先**从 A 提交的携带题中按报名顺序取用；用尽或未携带则临场生成（§8.2 出题端逻辑）。自己的题永远不会被用来考自己——题只在「对方答你出的题」的局中出现。
- **声誉收益**：你的携带题被对手作答且**未解出**（WA / TLE / 弃题）时，你 **+2 声誉**，即时入账并写入 `reputation_log`（source=`pvp_problem`）。
- **防刷上限**：
  1. **同一道携带题在同一场对决中至多计 1 次声誉**（一场最多 4 局，同题被重复抽用时只记第一次）；
  2. 单道题单届锦标赛声誉收益上限 **12 点**（约等于 32 人赛冠军一路打满 5 轮＋表演加场的自然天花板，不会因反复抽题而膨胀）；
  3. 携带题快照冻结，无法赛中改题数值。

### 2.7 冠亚军加场 【定稿】

决赛决出冠亚军后，追加一场**表演加赛**：

- 对阵：冠军 vs 亚军；冠军执先手出题权；**启用【考察出题质量】**（未解出 → 出题方 +2，见 §8.2）；双方均可使用携带题。
- 结果**不影响名次与主奖励**；胜方额外 **+5 声誉**。
- 定位为纯观赛内容：战报在全服公告位高亮展示，是每届赛事的收尾节目。

### 2.8 奖励发放 【定稿】

管理员创建时可配置各名次奖励（tag-card 除外，见下）；**默认模板**：

| 名次 | 默认奖励 |
|---|---|
| 冠军 | **tag-card ×1（冠军独占，不可配置移除）** ＋ 进阶石 ×2 ＋ 冠军奖杯 `trophy-champion` ×1（每次夺冠发放） |
| 亚军 | 进阶石 ×1 ＋ 洗练券 ×1 |
| 四强（3–4 名） | 洗练券 ×1 |
| 其余首轮胜者 | entry-ticket ×1（**返票**） |

- **tag-card 为 PVP 独占彩色道具**：`items.yaml` 中 `price: null`、sources 仅 PVP；剧情、历练、商城均不可获得——保持「全服身份象征」的稀缺叙事（GAME-DESIGN §13.2/§14 红线）。
- 进阶石经由 PVP 流出总量受管理员节制（GAME-DESIGN §7.3 建议冠军 2 颗即默认值）。
- 发放走统一幂等管线：`reward_grant(tournament_id, user_id, rank_tier)` 唯一键，调度器重跑不会重复发；前端提供「公示领奖」页，领取状态可见。

### 2.9 防作弊与公平（小规模够用版）

1. **服务端权威（重申）**：报名校验、快照、模拟、结算、发放全部在 API 服务端完成，客户端只读；接口鉴权＋基础限流遵循 GAME-DESIGN §17。
2. **快照机制**：报名截止冻结全员学员与携带题快照，哈希随对阵树公示——赛中任何人（含管理员）都无法改变比赛输入；暗改会在哈希比对中暴露。
3. **可复现结算**：种子确定性推导（§2.5），任何一场结果可离线重放核验。
4. **管理员操作审计**：`create_tournament`、报名截止前修改奖励配置、手动补偿发放、角色变更等敏感操作一律写入 `admin_audit_log(operator_id, action, payload_digest, created_at)`；审计页仅管理员可读。管理员**可以参赛**，但不得在报名截止后修改该届赛事的任何配置。
5. **报名唯一性**：单账号单届仅可报名一次（DB 唯一约束），报名接口限流。
6. **数值口径统一**：一切经济/道具数值来自 `docs/data/*.yaml` 导入表，代码零硬编码（项目数值配置纪律）。
